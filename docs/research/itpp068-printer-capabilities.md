# ITPP068 printer capabilities

## Source

The only source is the local PDF at the repo root: `ITPP068 Thermal Printer Linux Software Manual 220721-1.00.pdf`. It is 22 pages. It is untracked. The vendor's download link is dead, so keep this local copy.

This manual is a driver install guide for Linux CUPS. It is not a command reference. It does not list ESC/POS byte sequences. Page and section numbers below point to this manual. Where the manual is silent, this file says so and does not guess.

## Summary

The manual confirms four things: paper width, print speed, the cutter has a driver setting, and the printer accepts a raw TCP socket (the same method our code uses). The manual does not cover fonts, bold, underline, alignment, barcodes, cut command bytes, or real-time status queries. It points to a separate "ITPP068 Thermal Printer Windows Software Manual" for more detail, but that download link is also dead, so this file does not fetch it.

The current Go code (`internal/pos/escpos.go`) already sends working bytes for init, double-size, and cut. Those bytes came from the old TypeScript server and print correctly on the real hardware, per a comment in that file. This research does not change them.

## 1. Paper width and characters per line

Confirmed by the manual: the paper is 80 mm stock with 72 mm of printable width. The driver's Media Size setting reads "80(72mm) * 210mm" (p.10 Fig 2-12, p.15 Fig 2-21, p.19 §3.1 Fig 3-4). The CUPS printer defaults show the same figure in metric: `media=custom_71.97x209.9mm` (p.16 Fig 2-23, p.18 Fig 3-2).

Not in the manual: a table of characters per line at each font size. The manual has no font section at all.

A usable number needs one assumption the manual does not state: 80 mm thermal heads print at 203 dots per inch (8 dots per mm), which is the near-universal density for this printer class. That gives 72 mm × 8 = 576 dots of print width. The default ESC/POS Font A is 12 dots wide per character, so normal size fits about 48 characters per line. The kitchen ticket uses double width (`GS ! 0x11`, see Q2), which fits about 24 characters per line. Mark both numbers as derived, not confirmed. The fastest way to confirm them is a test print: send the digits "1234567890" repeated at normal size and at double size, and count where the line wraps on real paper. Suggest this as a first step for issue #34.

## 2. Font, bold, underline, alignment commands

Not in the manual. There is no command reference section. The manual only shows driver-level settings (paper size, cut, cash drawer, buzzer, logo), not the raw ESC/POS bytes behind them.

What the current code sends, for reference (`internal/pos/escpos.go`, not `pos.js` — the ESC/POS bytes live in the Go server, and a code comment there says they came from the old TypeScript server and are known to print correctly on the real printer):

- `ESC @` (`0x1b 0x40`) — initialise printer.
- `GS ! 0x11` — double width and double height on. Used for the kitchen ticket.
- `GS ! 0x00` — double width and double height off.

The code does not send bold, underline, or alignment commands today. This research does not invent new bytes for them, per the "do not derive them again" note in `escpos.go`. Any future need for bold/underline/alignment should be verified against the real printer, the same way the existing bytes were.

## 3. Barcode or QR printing

The manual does not document a barcode or QR command. It does show one piece of indirect evidence: the printer's own self-test page prints a QR code (p.13, Fig 2-17). That page is generated by the printer's own firmware, not by a command the manual explains, so this only proves the print engine is physically able to render a QR code. It is not proof that an application can trigger one over the network, and no command bytes are given.

## 4. Cut behaviour

The manual confirms the printer has a cutter, and that the Linux driver exposes cut settings: Page Cut Type, Document Cut Type, and Feed Cut After Job End (p.19 §3.2, Fig 3-5). The dropdowns shown in the screenshot are set to "No Cut," and the manual does not list the other choices in text, so it does not say whether the driver-level options distinguish full cut from partial cut.

The manual gives no ESC/POS byte sequence for either cut type. The current code already sends a cut command directly over the socket, bypassing the CUPS driver: `GS V 0x42 0x08` (`internal/pos/escpos.go`), which is the standard ESC/POS function-B partial cut with an 8-dot feed. So for this codebase, the practical answer is: it already does a partial cut, and it works on the real hardware. This research does not change that byte sequence.

## 5. Print speed and buffer limits

The printer's own self-test printout, shown in the manual, states "Speed : 300mm/s" (p.13, Fig 2-17). The same self-test also shows: firmware version 7.D08PA2N, interfaces USB, Serial (19200 baud, no parity, 8 data bits, 1 stop bit), and Ethernet (10M/100M), and protocol TCP/IP.

The manual says nothing about a print buffer, a queue depth, or how the printer behaves when several tickets arrive close together. There is no guidance here for order bursts. If bursts become a real concern, the safe next step is a timed test: send several kitchen tickets back to back over the socket and watch for dropped or corrupted output, rather than relying on a written spec that does not exist in this manual.

## 6. Real-time status queries (DLE EOT n, GS r n)

The manual is silent. It does not mention `DLE EOT n`, `GS r n`, or any real-time status query. It does not describe status response bytes or what any bit in a status reply means. Those commands and their bit layouts are part of the general Epson ESC/POS reference, not this vendor's manual, so this file does not assert bit meanings here — that check belongs to issue #34, against the real printer.

What the manual does confirm, which matters for #34: the printer accepts plain raw-socket printing. The Linux install steps use a CUPS "AppSocket/HP JetDirect" connection with a URI like `socket://<printer-ip>` (the manual's own example shows `socket://hostname:9100`, p.12 §2.3 step 3, Fig 2-16). This is the same raw TCP approach `internal/pos/printer.go` already uses (`net.DialTimeout("tcp", address, ...)`), so nothing about the network path should block a status query from working, if the firmware supports one.

Issue #20 already found the real blocker in code, not in the manual: `sendEscPos` in `internal/pos/printer.go` opens the connection, writes the payload, and closes it with `defer connection.Close()` — it never reads a reply. So even if the printer answers a `DLE EOT n` or `GS r n` query on the same TCP connection (which is how these commands work on Epson-compatible printers generally), the current code would never see it. Confirming that the ITPP068 actually answers, and reading the reply on the same connection before closing it, is exactly the real-device check issue #34 should do. This research does not change `printer.go`.

## Proposal: item name wrap and Side placement

This uses the derived character counts from Q1 (48 chars normal, 24 chars double width), which are not confirmed by the manual and should be checked with a real test print before the Side feature ships.

The menu already has the longest names to test against (`internal/pos/menu.go`): "The Harvest Toastie" is the longest item name at 20 characters. The longest side is "Applesauce" or "Sour cream," both 10 characters.

**Kitchen ticket.** The kitchen ticket prints in double width (`GS ! 0x11`), budget about 24 characters per line. The current line format is `"%d  %s"` (quantity, two spaces, upper-case name), which spends 3–4 characters on the quantity and spacing, leaving about 20 characters for the name. "THE HARVEST TOASTIE" is 20 characters, so it just fits; any longer name would wrap. Propose: keep the item name on its own line as today. Print the Side on the line right below it, same double width so the scout reads it at a glance without switching focus, indented two spaces so it reads as "belonging to" the item above it, for example:

```
1  POTATO PANCAKE
  SOUR CREAM
```

**Customer receipt.** The receipt prints at normal width, budget about 48 characters per line, so wrapping is not a practical concern for any current item name. The current line format is `"%d x %s"` followed by a price line. Propose: add the Side as its own indented line between the item name and the price, at normal size (no need for double width here, since the receipt is read by an adult, not a scout at the grill), for example:

```
1 x Potato Pancake
  Sour Cream
  $10.00
```

Both placements reuse the layout the code already has (one line per printed element, joined with `\r\n`), so this needs a new line in `encodeLines`'s input, not a new ESC/POS command.
